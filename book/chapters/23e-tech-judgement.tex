\section{面对新模型与新缩写，怎么判断它值不值得学？}
\label{intro:23e-tech-judgement}
\chaptercompass{新技术好不好，要用什么证据判断？}{核对目标瓶颈、基线、质量指标、预算与失败条件。}{同一任务／相同约束 $\to$ 可对照的指标}{技术选型不等于新的参数训练算法}
\modelpipelinefocus{8}{技术判断与系统约束}


我们已从语言模型走到系统工具、部署，再回看 RoPE、MoE、GQA 等架构。
技术名称不断变化，但读者不必为了追赶每个缩写而重新背一遍名词表。
更重要的是拿到一个新技术时，能独立判断\textbf{它解决了哪个瓶颈，
用什么证据证明，付出了什么代价，以及哪些条件下会失效}。

\subsection{先把“改进”分到五层，而不是混在一起}

\begin{enumerate}
\item \textbf{表示层：}Tokenizer、Embedding、位置表示如何编码输入？
这些改动首先改变输入表示；回答质量是否提升，要用相同任务另行评测。
\item \textbf{模型计算层：}Attention、FFN、MoE、归一化与缓存改变什么？
区分训练 FLOPs、解码延迟、KV 内存和总参数量。
\item \textbf{训练与反馈层：}预训练、SFT、偏好优化、RLVR 是否修改权重？
数据、奖励与评测目标一致吗？
\item \textbf{推理策略层：}采样、验证、搜索、上下文示例是否使用额外计算，
但通常保持同一权重？
\item \textbf{系统层：}RAG、工具、MCP、Workflow、Agent/A2A 是怎样连接
资料与授权动作的？安全责任归谁？
\end{enumerate}
例如“模型接入了新的报表搜索工具”，首先是\textbf{系统与证据来源}变化；
这是系统和证据来源的改进；模型宽度仍由权重配置决定。

\subsection{Scaling Laws：更多参数一定更聪明吗？}

经典缩放规律研究在一定实验范围内发现：
语言模型的\textbf{验证损失}常随参数量、训练 Token 与计算预算
呈较规律的变化趋势。Kaplan 等（2020）讨论了这些关系，
见 \href{https://arxiv.org/abs/2001.08361}{Scaling Laws for Neural Language Models}。
Hoffmann 等（2022）进一步研究给定训练计算量时
\textbf{模型参数和训练 Token 应如何分配}，见
\href{https://arxiv.org/abs/2203.15556}{Training Compute-Optimal Large Language Models}。

这是\textbf{经验规律}，体现增加资源时的总体趋势；单题是否答对仍取决于具体任务。
参数、数据、算力与质量互相制约；
评测分布、推理预算以及是否有工具，也会改变最终结果。
规模带来可扩展性，任务定义、数据质量和可靠性验证决定它能否转化为实际收益。

\subsection{Bitter Lesson：计算与通用方法为何常被重视？}

Richard Sutton 在
\href{http://www.incompleteideas.net/IncIdeas/BitterLesson.html}{The Bitter Lesson}
中主张，长期来看，能够借助增长的计算规模进行学习或搜索的通用方法，
往往比大量手写领域规则更有扩展性。
这是一种关于研究历史与方法选择的\textbf{经验观点}，
不是针对每一个数据量、预算和应用场景的严格证明。
在受限硬件、特定安全规则和明确工作流中，
手写约束与专家知识仍然可以非常重要。
\hyperref[part:learning]{开篇的学习与训练部分}问“为什么规则难以写尽”，在这里得到了一次回响：
\textbf{让系统学会一般模式，与让应用遵守明确规则，并不矛盾。}

\subsection{莫拉维克悖论：容易说清的事情，不一定容易做成}

所谓\textbf{莫拉维克悖论（Moravec's paradox）}，
是 AI 与机器人研究史中的一项\textbf{观察和解释框架}：
人类觉得“需要思考”的棋类、符号运算等任务，
在一定程度上能够被计算机用形式化规则处理；
人类不假思索完成的视觉辨认、触觉操作、
在陌生环境中保持身体平衡等任务，
在真实世界中反而需要复杂的感知与控制。

直觉上，符号任务常具有明确的输入、状态和计分方式；
现实操作要应对遮挡、传感器噪声、接触力和环境变化，
很难仅靠一串标准答案穷尽。
\textbf{它描述了典型能力差异，具体任务难度仍取决于环境与评价方式}：
现代视觉识别已经取得长足进展，
一些电子游戏与规划任务仍很难，
而机器人在受控场景中的表现也不能直接外推到所有环境。
真正可用的问题是：\textbf{训练分布以外，哪些感知和行动条件会失败？}
阅读可参考
\href{https://en.wikipedia.org/wiki/Moravec%27s_paradox}{历史背景概述}；
不要把悖论当作当代能力排行榜。

\subsection{“架构创新空间正在收窄”是可检验的争议观点}

一种立场认为：大规模预训练、Transformer 的成熟工程栈、
标准化评测和推理服务的规模效应，
使很多任务上\textbf{沿既有架构改进数据、训练和系统效率}
更容易获得可复现收益。
这种判断应由\textbf{同等算力、数据、延迟和质量约束下的实验}支持，
需要核对公开的结构信息及同条件下的实验，而不是推断自宣传用语。

另一种立场指出：序列建模并非只有标准全量 Self-Attention。
例如\href{https://arxiv.org/abs/2312.00752}{Mamba}
等状态空间路线、
\href{https://arxiv.org/abs/2412.06464}{Gated DeltaNet}
等状态更新结构以及混合层，
探索了长序列信息流和运行成本的不同权衡。
一些方向可能在特定长度、硬件或吞吐设置下更有优势，
同时有自己的训练稳定性、随机访问和质量问题。

\textbf{结论：架构选择是一项受测量条件约束的工程决策。}
只有在相同算力、数据、硬件与质量指标下比较，
才能判断一种结构是否更适合目标任务。其余主张随证据更新。

\subsection{拿到宣传语，先做一次拆解}

假设听到一句：“新注意力让上下文扩大十倍，速度提升十倍，
因此所有业务的答案都会更准确。”
先要求补齐缺失的证据：
\begin{itemize}
\item \textbf{比较对象：}与哪一个基线、哪一种实现、哪一个硬件平台比较？
\item \textbf{指标定义：}更快指首 Token 延迟、吞吐还是总运行时间？
上下文变长不自动等于能准确找到远处证据。
\item \textbf{质量代价：}长程检索、普通对话、代码等任务是否都测过？
有没有关键回归？
\item \textbf{实验条件：}输入长度、并发数、精度、缓存策略和训练量是否相同？
\item \textbf{应用边界：}引用核查、工具权限、失败处理有没有另外验证？
\end{itemize}
一项新技术可能主要减少显存，
另一项主要增加训练期活跃参数，
第三项主要减少人为操作；\textbf{三者不能只按同一个“更先进”排名}。


\subsection{从交叉熵到困惑度：评测先要明确量尺}
\phantomsection\label{concept:perplexity}

语言模型常用\textbf{困惑度（Perplexity, PPL）}概括
保留测试集上的平均下一 Token 交叉熵。
如果交叉熵按自然对数计算，每个 Token 的平均损失为 $L$，
则 $\mathrm{PPL}=e^L$。

\begin{example}[breakable=false]
\noindent\emph{沿用三位置前向实验的损失}\par
本书三维贯通例初始平均交叉熵为 $L=1.798430$，
因此
\[
\mathrm{PPL}=e^{1.798430}\approx 6.04.
\]
这不是六个候选 Token，也不是准确率 $1/6.04$。
它表示在相同分词、预测位置和数据口径下，
模型给真实序列分配概率的几何平均倒数。
\end{example}

\textbf{评测（Evaluation）}至少区分四类量尺：
语言概率可看交叉熵和 PPL；有标准答案的任务可看准确率、
通过率或 exact match；RAG 系统要检查\textbf{证据覆盖与引用准确率}；
Agent 还需记录工具成功率、越权率、延迟、成本和失败恢复。
不同 Tokenizer 的 PPL 数值通常不能直接跨词表比较。

\subsection{为什么 Benchmark 高分仍需要复核？}

\textbf{Benchmark（基准测试）}必须说明数据构造、题目来源、
评分脚本、样本量与置信区间。若测试题或答案出现在训练集、
微调集、检索库或反复调参所见的测试集里，
就可能发生\textbf{评测污染（Benchmark Contamination）}。
这时榜单分数可能高估真实泛化能力。
在可行时用时间隔离的保留集、去重与来源追踪，并对新题复测。

\textbf{数据偏见与模型偏见}同样需要评估：
训练资料是否遗漏特定语言、地区或群体？
同一服务在不同用户场景下是否出现系统性的错误差异？
标注规则由谁确定，错误由谁承担？
同时评估隐私数据泄露、未经授权的操作与提示注入，
不能以单一“平均得分”代替分组指标和真实事故分析。
人工审核可提供质性证据，但需记录审核者分歧和判定规则。

\subsection{把全书压缩成五道可以反复使用的问题}

读完任何新的架构、训练算法或 Agent 系统，试着回答：
\begin{enumerate}
\item 上一个方法\textbf{哪一步不够用}，能否构造反例？
\item 新方法的\textbf{输入、输出、形状或调用协议}是什么？
\item 有什么可复算的\textbf{数字、测试或可追溯来源}？
\item 哪一项\textbf{成本或风险}被转移到别处？
\item 什么情形下应该\textbf{退回更简单的方法}？
\end{enumerate}

\chapterchecktasks{23e-tech-judgement}{正文基础三题}{
\item \textbf{分类：}某产品宣布“更聪明又更便宜”。在模型结构、训练、推理系统、评测与产品体验这几层中，至少分辨出三种可能的改动来源。
\item \textbf{手算：}缓存元素由 $100$ 降到 $50$，下降比例是多少？这个数字本身说明了任务准确率或首 Token 延迟吗？
\item \textbf{找错：}宣传 A 用长输入、旧硬件测试，宣传 B 用短输入、新硬件测试，然后将差距完全归因于新架构。如何指出混杂因素？
}
\chapterrecallanswer{判断技术改进要先确定改动层级、实验对照与质量目标，再综合比较成本与失败条件。}



\begin{conclusion}
评估新技术，先确认\textbf{它修改哪一层、解决什么问题}，
再核对可复算的证据、成本与失败条件。
明确需求后，才决定是否深入研究它的实现。
\end{conclusion}
